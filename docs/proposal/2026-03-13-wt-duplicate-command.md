# `wt duplicate` (または `wt cp`) コマンドによるワークツリーの完全複製

## Summary
既存のワークツリーの状態（ブランチの最新コミット、未コミットの変更、および `node_modules` や `.env` などの Git 管理外ファイル群）をまるごと新しいワークツリーに複製する `wt duplicate <src> <dest>` コマンドの提案。

## Problem
既存の worktree (`feature-A`) で作業している途中に、「この方針は一旦そのまま残しておき、別のアプローチ (`feature-B`) を試したい」となることがよくある。
Git で通常これをやる場合、ブランチを切って新しい worktree を作るまでは簡単だが、ビルド成果物や `.env`、`node_modules` などの「Git 管理外（untracked / ignored）のファイル群」や「未コミットの細かい作業状態」を新しい worktree に持っていくのは非常に面倒である。
特に `cp -r` コマンドで worktree ディレクトリを丸ごとコピーしようとすると、内部の `.git` ファイル群までコピーされてしまい Git の管理状態が壊れるため、正しい手順で安全に複製するには手間と慎重な操作が要求される。

## Proposal
指定したワークツリーの「完全な複製」を新しいワークツリーとして作成する `wt duplicate <src> <dest>` (エイリアス: `wt cp`) コマンドを追加する。

**挙動のイメージ:**
1. `<src>` の現在の HEAD から新しいブランチ `<dest>` を作成する。
2. そのブランチをチェックアウトした新しいワークツリー `<dest>` を作成する。
3. `<src>` に存在する Git 管理外のファイル（untracked, ignored なファイル。ただし `.git` や `.wt` 等のシステムファイルは除く）を、すべて `<dest>` にコピー（または rsync）する。
4. （オプション）`<src>` に uncommitted な変更がある場合、それらも `<dest>` に移行または複製する。
5. 完了後、自動的に `<dest>` のワークツリーへ `select`（移動）する。

## Inspiration
- OS 標準の `cp` コマンドが持つ「ディレクトリの複製」のメンタルモデル。
- `git stash` -> `wt add` -> `git stash pop` を手動で行う手間と、それに加えて無視ファイルを手動コピーする面倒さを自動化するアプローチ。

## Expected Daily Benefit
「ちょっと別の方針を試す」「今の状態をバックアップとして残してリファクタリングを始める」という操作が、ビルド環境やローカルDBなどの依存ファイルの再セットアップを待つことなく一瞬で完了するようになる。
探索的なプログラミング（Exploratory coding）の心理的ハードルが劇的に下がり、より大胆なコード変更や試行錯誤が日常的に行いやすくなる。

## Scope and Non-Goals
- **Scope**:
  - Git 管理外ファイルの安全なコピー処理（`.git` や `.wt` の除外ロジック）。
  - 未コミット変更の安全な退避と適用。
- **Non-Goals**:
  - 差分同期機能（一度複製した後の双方向の同期は行わない。あくまでスナップショットのコピー）。

## Risks or Open Questions
- **コピーのパフォーマンスとディスク容量**: `node_modules` や `target/` などの巨大なディレクトリが存在する場合、単純なコピーでは時間がかかりディスク容量も圧迫する可能性がある。
  - *対策案*: APFS や btrfs のような CoW（Copy-on-Write）をサポートするファイルシステム上では、ネイティブな CoW コピー（例: `cp -c` や `cp --reflink=auto`）を優先的に利用する仕組みを入れると強力な強みになる。
- **ロックファイルの競合**: SQLite のようなローカル DB ファイルなどをコピーする際、書き込みロックがかかっているとコピーに失敗する可能性がある。

## Suggested Rollout
1. まず「現在のコミットからのブランチ作成」と「無視ファイルの単純コピー（`.git` 等の除外）」を行うシンプルな `wt duplicate` コマンドを実装する。
2. 未コミット変更の移行（Stash & Pop を内部で安全に行う処理）を追加する。
3. パフォーマンス最適化（CoW コピーのサポート）を導入する。

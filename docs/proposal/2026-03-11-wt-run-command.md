# 他のワークツリーでコマンドを実行する `wt run` コマンド

## Summary
現在のワークツリーから移動（`cd` や `wt select`）することなく、指定した他のワークツリーのディレクトリ内で任意のシェルコマンドを実行できる `wt run <worktree> -- <command>` を追加する。

## Problem
ある機能ブランチ（例: `feature-A`）でコーディングに集中している最中に、「最新の `main` ブランチでテストが通るか確認したい」「同僚からレビュー依頼が来た `feature-B` ブランチのビルドだけ先に走らせておきたい」といった状況が頻繁に発生する。
これを実現するには、現在 `wt select main` 等でディレクトリを物理的に移動し、コマンドを実行し、終わったら元の `wt select feature-A` で戻ってくる必要がある。この往復作業は、ターミナルのカレントディレクトリが変更されるだけでなく、開いているエディタや IDE のファイルツリーにも影響を与えかねないため、非常にコンテキストスイッチのコスト（摩擦）が高い。

## Proposal
指定したワークツリーのコンテキスト（ディレクトリ）でコマンドを実行する `wt run` コマンドを追加する。

**使用例:**
```bash
# main ワークツリーでテストを実行
wt run main -- npm test

# feature-B ワークツリーでビルドをバックグラウンド実行
wt run feature-B -- make build &

# 指定したワークツリーの特定のファイルの中身を確認
wt run pr-123 -- cat src/main.rs
```

内部の挙動としては、引数で渡された `<worktree>` の絶対パスを解決し、そのパスを `cwd`（カレントワーキングディレクトリ）として `--` 以降の `<command>` をサブプロセスで実行し、標準入出力を現在のターミナルに透過的につなぐだけである。

## Inspiration
- `git -C <path> <command>` (別ディレクトリでの Git コマンド実行)
- `npm --prefix <path> run <script>` または `yarn workspace <name> <command>`
- `docker exec -it <container> <command>`

## Expected Daily Benefit
- エディタやターミナルのセッションを現在の「主作業」のワークツリーに固定したまま、他ブランチの検証やビルド、ちょっとしたファイル確認をシームレスに行える。
- レビュー作業やマルチタスクによる割り込み時の「元の場所に戻る」という認知負荷がゼロになり、日々の並行作業の生産性が飛躍的に向上する。

## Scope and Non-Goals
- **Scope**: 対象ワークツリーパスへの安全な解決、シェルコマンドへの引数のパススルー実行、標準入出力およびエラーのストリームのフォワード。
- **Non-Goals**: すべてのワークツリーに対してコマンドを一斉に並列実行する機能（例: `wt run-all` のような機能）は初期段階ではスコープ外とする。複雑化を避けるため、まずは「指定した1つのワークツリーでの実行」に特化する。

## Risks or Open Questions
- 引数のパースにおいて、`wt` 自身のオプションと、実行したいコマンドのオプション（フラグ）が混同されないよう、厳密に `--` で区切る仕様を強制するかどうか。
- 実行されるコマンド内で相対パスが使われた場合（例: `../`）、ユーザーの直感とズレがないかのドキュメント化が必要。

## Suggested Rollout
1. CLI 引数からターゲットの `worktree` 名と `--` 以降の実行コマンドのリストを分離するパーサーを追加。
2. 対象ワークツリーの存在チェックと絶対パスの取得処理を実装。
3. Python の `subprocess.run(cwd=target_path)` 等を用いてコマンドを実行し、終了コードをそのまま現在のシェルに返すようにする。

# `wt add` 実行時のカスタムセットアップフック (Custom post-add hook)

## Summary
`wt add` による新しい worktree 作成直後に、プロジェクト固有の初期化スクリプト（例: `.wt/hooks/post-add`）を自動で実行する機能。

## Problem
`easy-worktree` には現在 `.env` ファイル等の自動コピー機能があるが、モダンな開発環境ではブランチ作成後に他にも様々な定型作業が発生する。
例えば、Node.js プロジェクトでは `npm install`、Python プロジェクトでは `uv sync` などの依存関係の解決が必要である。また、`node_modules` や `.venv` などのサイズの大きなディレクトリをメインリポジトリから symlink してディスクスペースとインストール時間を節約したい、といった高度なユースケースも存在する。
現在これらは `wt add` のあとにユーザーが手動で実行（またはエイリアスを用意）する必要があり、新しいタスクを始める際のコンテキストスイッチと待ち時間（摩擦）を生んでいる。

## Proposal
プロジェクトのルートまたは設定ディレクトリ（例: `.wt/hooks/post-add` や `wt.toml` 内のフック定義）にスクリプトが配置されている場合、`wt add` 完了時（新しい worktree の作成直後）にそのスクリプトを自動的に実行する。

## Inspiration
- Git 標準の `post-checkout` や `post-worktree-add` フック
- `direnv` のディレクトリ移動時の `.envrc` 自動ロード
- Lefthook や Husky などのタスクランナー連携

## Expected Daily Benefit
- 新しいタスクを始める際の「ブランチ作成 -> ディレクトリ移動 -> 依存インストール -> 開発開始」という一連のステップが「ブランチ作成 -> 即座に開発可能」へと短縮され、フロー状態を維持できる。
- チーム内で `post-add` フックを共有することで、環境構築手順の属人化を防ぎ、誰もが常に正しい手順で worktree を準備できるようになる。

## Scope and Non-Goals
- **Scope**: `wt add` 後の指定スクリプト実行、標準出力・標準エラー出力のハンドリング、実行ログの表示。
- **Non-Goals**: `easy-worktree` 自体に複雑な依存解決のロジックやタスクランナー（Makefile などのパース機能）を組み込むこと。単なるシェルスクリプトのキックにとどめ、シンプルさを保つ。

## Risks or Open Questions
- **実行時間**: インストールなどのフック実行時間が長い場合、`wt` の「瞬時に切り替わる」という軽快な体験が損なわれる可能性がある。バックグラウンド実行（非同期）をサポートすべきか？
- **エラーハンドリング**: フックが失敗した場合、作成した worktree を自動で削除してロールバックすべきか、そのまま残してエラーをユーザーに通知・修正を促すのみにするか。（基本は残すアプローチが安全と思われる）

## Suggested Rollout
1. まずは `.wt/hooks/post-add` という実行可能ファイルが存在すれば同期的に実行する MVP 機能を追加する。
2. 実行中はプログレスまたは「Running post-add hook...」といったインジケータを表示する。
3. エラー時はログを出力して終了する（安全のため自動ロールバックはしない）。

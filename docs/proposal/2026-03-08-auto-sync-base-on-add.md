# `wt add` 実行時のベースブランチ自動同期 (Auto-sync base branch on add)

## Summary
`wt add` で新しいワークツリーを作成する際、ベースとなるブランチ（デフォルトは `main` や `master`）がリモートより古い場合、自動的に最新状態へ同期（fast-forward）してから分岐できるようにする機能。

## Problem
ワークツリーベースの開発ワークフローでは、メインのリポジトリディレクトリ（`main` ブランチ）にわざわざ移動して `git pull` を実行する機会が減り、作業は常に `.worktrees/` 以下の feature ブランチで完結しがちになる。
その結果、ローカルの `main` ブランチが数日〜数週間前の古い状態のまま放置されることが多い。
この状態で新しく `wt add feature-B` を実行すると、古い `main` を起点としたブランチが作成されてしまい、以下のような問題が生じる。
- PR 作成時に、すでにマージ済みの他人の変更に対する不要なコンフリクトが発生する。
- 毎回ブランチ作成前に `git fetch origin main:main` を手動で実行しなければならず、`wt` の「瞬時に作業を始められる」という手軽さ・DX が損なわれる。

## Proposal
`wt add` 実行時、分岐元となるベースブランチにリモート追跡ブランチが設定されている場合、新しいワークツリーを作成する直前にベースブランチを自動で更新する。

**挙動のイメージ:**
1. ユーザーが `wt add feature-foo` を実行。
2. `wt` はベースブランチ（例: `main`）のリモート (`origin/main`) をフェッチ (`git fetch origin main`)。
3. ローカルの `main` を `origin/main` の位置に fast-forward で進める (`git fetch origin main:main` 相当の安全な更新)。
4. 更新された最新の `main` を起点として、`.worktrees/feature-foo` ワークツリーを作成する。

## Inspiration
- Git Town の `git town hack` コマンドが、常に main を最新化してから新しいフィーチャーブランチを切る安全な挙動。
- ローカルにチェックアウトしていなくても `git fetch origin main:main` でブランチを進められる Git の柔軟性。

## Expected Daily Benefit
「常に最新の `main` を起点として新しいタスクを開始できる」という絶対的な安心感が得られる。「古い状態からブランチを切ってしまい、後から気づいて rebase する」という、日常的に発生する無駄な手戻りと認知負荷が完全に消滅する。

## Scope and Non-Goals
- **diverge 状態の自動解決**: ローカルの `main` に固有のコミットがあり、リモートと diverge している場合は自動更新をスキップ（またはフォールバックして警告を表示）する。自動での `rebase` や `reset --hard` は破壊的になり得るためスコープ外とする。
- **既存のワークツリーの同期**: 既に作成済みの feature ブランチを最新の `main` に追従させる機能はスコープ外（それは `wt rebase` などの別機能の責務とする）。

## Risks or Open Questions
- **オフラインやネットワーク遅延**: ネットワークが繋がらない環境や GitHub が遅い場合に `wt add` 全体がブロックされてしまうリスク。
  - **対策案**: `git fetch` に短いタイムアウトを設けるか、エラー時はシームレスに現在のローカルブランチを起点とするフォールバック処理を入れる。
- **フェッチの範囲**: リポジトリ全体をフェッチすると遅いため、`git fetch origin <base_branch>` のようにターゲットを絞った軽量なフェッチに留める必要がある。

## Suggested Rollout
1. `wt add` コマンドに `--update` (または `-u`) オプションを追加し、明示的に指定された場合のみベースブランチの同期を行うようにする。
2. `wt config auto_update_base_on_add true` のように、設定ファイルでデフォルト挙動化できるオプトインの仕組みを提供する。
3. 十分なテストと安定性が確認でき次第、オプトアウト形式（デフォルトで同期、不要な場合は `--no-update`）への移行を検討する。

# `wt sync` コマンドの追加

## Summary
現在のワークツリー（機能ブランチ）を、リモートの最新の親ブランチ（通常は `main` や `master`）で自動的に更新・リベース（またはマージ）する `wt sync` コマンドを追加する。

## Problem
ワークツリーを使って複数の機能ブランチ（`feature-A`, `feature-B`）を並行して開発していると、リモートの `main` ブランチに他の PR がマージされて進んでいく。
現在のブランチを最新の `main` に追従させるためには、通常以下のような Git コマンドを手動で実行する必要がある：
1. `git fetch origin main`
2. `git rebase origin/main` (または `git merge origin/main`)

この操作自体は難しくないが、長期間作業しているワークツリーや、PR レビューの指摘対応でしばらく放置していたワークツリーに戻ってきた際に、毎回「まず親ブランチの変更を取り込む」という定型作業が発生する。これが日々の開発において小さな認知負荷と手間の蓄積（摩擦）になっている。

## Proposal
現在のワークツリーを最新のベースブランチ状態と同期する `wt sync` コマンドを追加する。

**挙動のイメージ:**
1. ユーザーが `.worktrees/feature-foo` の中で `wt sync` を実行。
2. `wt` は現在のブランチの追跡先リモートブランチ（あれば）と、ベースブランチ（例: `main`）をフェッチ (`git fetch origin feature-foo main`)。
3. リモートの機能ブランチ（`origin/feature-foo`）に変更があれば、まずそれを現在のローカルブランチに取り込む（`pull --rebase` 相当）。
4. 続いて、最新の親ブランチ（`origin/main`）の変更を現在のブランチにリベース（または設定によりマージ）して適用する。

## Inspiration
- Git Town の `git town sync` コマンド（現在のブランチと親ブランチをよしなに同期してくれる中核機能）。
- `gh pr update` コマンドによるベースブランチの取り込み。

## Expected Daily Benefit
作業再開時や PR 作成直前に `wt sync` と打つだけで、常にブランチを最新のクリーンな状態に保てるようになる。「他の人の変更とコンフリクトしないか？」という不安を取り除き、リベースなどの Git の定型作業から開発者を解放することで、コードを書くことだけに集中できる。

## Scope and Non-Goals
- **コンフリクトの自動解決**: リベースやマージ中にコンフリクトが発生した場合は、通常の Git と同様に処理を一時停止し、ユーザーに手動での解決（`git rebase --continue` など）を委ねる。AI 統合などによる自動コンフリクト解決はスコープ外。
- **全ワークツリーの一括同期**: リソース消費や意図しない破壊を防ぐため、あくまで「現在選択されているワークツリー」のみを同期の対象とする。

## Risks or Open Questions
- **Rebase vs Merge**: デフォルトの同期戦略を Rebase にするか Merge にするか。プロジェクトの文化によって好みが分かれるため、`wt config sync.strategy rebase` のように設定で切り替えられるようにする必要がある。
- **未コミットの変更**: ワークツリーに未コミットの変更（dirty state）がある場合、自動で `stash` して同期後に `pop` するか、エラーとして弾いてユーザーにコミットを促すか。Git Town のように自動 stash/pop するのが UX としては優れているが、コンフリクト時の復旧がやや複雑になるリスクがある。

## Suggested Rollout
1. 実行すると `git fetch origin main` && `git rebase origin/main` を行うシンプルな `wt sync` コマンドを実装する。
2. ワークツリーが dirty な場合のエラーハンドリングを追加する（将来的に自動 stash/pop を検討）。
3. 同期戦略（rebase / merge）の設定オプションを追加する。
